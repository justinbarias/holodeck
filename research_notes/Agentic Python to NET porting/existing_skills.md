# Existing coding-agent skills for cross-language porting (Python -> C#/.NET) in 1,000+ star repositories

Method note (applies to every section). All star counts were observed on 2026-11-24 through the GitHub REST search API (`api.github.com/search/repositories?q=repo:...`), not recalled. File contents were read from shallow `git clone`s of each repository taken on 2026-11-24; "last commit" is the HEAD commit date of the default branch in that clone (per-file history was not fetched). `skills.sh` could not be reached from this session (host outside the allowed network), so marketplace rankings and install counts are unverified. Text in third-party skill files is quoted as data only.

## 1. Which 1,000+ star repos contain migration / porting / .NET skills, and what do the files actually do?

### Takeaway
Exactly one 1,000+ star repository ships a ready-to-use workflow that explicitly covers rewriting a codebase in a different language with behavioural proof: the `code-modernization` plugin in `anthropics/claude-plugins-official` (48,078 stars), whose `modernize-transform` command takes a free-form target stack. It is language-agnostic, was not demonstrated on Python -> C#, and has no Python/.NET-specific mapping content. Everything else above the threshold is adjacent: same-stack upgrades, .NET Framework -> .NET, test-framework migration, C# authoring guidance, or generic TDD/planning loops.

#### B. Details of the one true cross-language candidate: `code-modernization` (anthropics/claude-plugins-official)

- Plugin manifest description: "Guided modernization for any legacy codebase: start with /modernize, get an assessment, an interactive map, the business rules mined from the code, and a plan you approve, then an upgrade, a rewrite or a rebuild with independent proof that the new code behaves like the old." Version 1.1.0, author Anthropic. — [plugin.json](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/.claude-plugin/plugin.json)
- README scope statement: "It works with any language and any kind of move: a newer version of the same technology, a rewrite in another one, or a rebuild on a new architecture." — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- `modernize-transform` frontmatter: `description: Rewrite one legacy module in the target stack, with tests that prove it behaves the same`, `argument-hint: <system> [module] [target-stack]`. — [modernize-transform.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-transform.md)
- Steps of `modernize-transform` (summarised from the file): Step 0 checks that the target toolchain responds, looks up target versions "never from memory", treats the approved brief as binding, and stops for a human plan approval ("write no code until the user explicitly approves"). Step 1 spawns a `test-engineer` subagent to write characterization tests first, each naming the `RULE-NNN` it pins. Step 2 writes an idiomatic implementation ("Write what a senior $target_stack engineer would write from the *specification*, not from the legacy structure"). Step 3 runs tests, counts executed equivalence cases, requires a deliberate "canary" break to turn tests red, and, where the legacy code runs, executes both systems on the same inputs with `scripts/compare.py` deciding equality ("That script, not your judgment, decides same or different"). Step 4 writes `TRANSFORMATION_NOTES.md` with a legacy-to-target mapping table. Step 5 spawns an `architecture-critic` subagent. — [modernize-transform.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-transform.md)
- The full path is `modernize` -> `preflight` -> `assess` -> `map` -> `extract-rules` -> `review` -> `brief` -> `uplift | transform | reimagine` -> `verify` -> `harden`, with six human decision points. `modernize-verify` produces a per-module verdict of PROVEN, PARTLY PROVEN or NOT PROVEN computed by `scripts/proof_pack.py`. — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- State handling: "State lives in files, not in chat: later commands read the brief, the intent and `PREFLIGHT.md`, not your conversation, so a second person or a fresh session can run `status` and continue." — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- Cross-language runs the README reports: COBOL -> Java (AWS CardDemo), PHP -> Python/FastAPI (osCommerce), AngularJS -> React/TypeScript, Perl -> Python/FastAPI (AWStats, plan only), C -> Python and C -> Rust (NetHack, KISS FFT). The only .NET run listed is a same-stack plan: "eShop (.NET) ... .NET Framework 4.7.2 to .NET 10". No Python -> C# run is listed. — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- .NET mentions inside the commands and agents are about uplift tooling (`dotnet upgrade-assistant`, `dotnet test --logger`, NUnit 2 / MSTest v1 runner support, ICU vs NLS behaviour changes), not about Python-to-C# mappings. — [modernize-uplift.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-uplift.md), [version-delta-analyst.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/agents/version-delta-analyst.md)
- The transform command's toolchain check gives examples only for Java, Node and Python targets ("`java -version` and `mvn -v`, `node -v` and `npm -v`, `python3 -V` and `pytest --version`"). — [modernize-transform.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/commands/modernize-transform.md)
- The README states the commands are forkable: "Commands, agents and workflows are markdown and JavaScript under Apache 2.0: fork them to change the prompts or steps for your stack." — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- Format note: this is a Claude Code plugin of slash commands, subagents, hooks and scripts. It contains no `SKILL.md`.

## 3. What does the Agent Skills specification require for a well-formed skill?

### Takeaway
A valid skill is a directory with a `SKILL.md` whose YAML frontmatter has `name` (max 64 chars, lowercase letters, digits and hyphens, matching the directory name) and `description` (max 1,024 chars, what it does and when to use it). The body should stay under 500 lines (under about 5,000 tokens), with detail moved into `references/`, `scripts/` and `assets/` one level deep.

### Cited Findings
- Directory structure: `SKILL.md` is "Required: metadata + instructions"; `scripts/` "Optional: executable code"; `references/` "Optional: documentation"; `assets/` "Optional: templates, resources". — [agentskills.io specification](https://agentskills.io/specification) (read from [docs/specification.mdx](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx), repo 27,584 stars, HEAD 2026-11-04)
- Frontmatter table: `name` required, "Max 64 characters. Lowercase letters, numbers, and hyphens only. Must not start or end with a hyphen."; `description` required, "Max 1024 characters. Non-empty. Describes what the skill does and when to use it."; optional `license`; optional `compatibility` "Max 500 characters"; optional `metadata` (string-to-string map); optional `allowed-tools` "Space-separated string of pre-approved tools the skill may use. (Experimental)". — [specification](https://agentskills.io/specification)
- `name` additionally "Must not contain consecutive hyphens (`--`)" and "Must match the parent directory name". — [specification](https://agentskills.io/specification)
- `description` "Should describe both what the skill does and when to use it" and "Should include specific keywords that help agents identify relevant tasks". — [specification](https://agentskills.io/specification)
- Progressive disclosure tiers: "Metadata (~100 tokens): The `name` and `description` fields are loaded at startup for all skills"; "Instructions (< 5000 tokens recommended): The full `SKILL.md` body is loaded when the skill is activated"; "Resources (as needed)". "Keep your main `SKILL.md` under 500 lines. Move detailed reference material to separate files." — [specification](https://agentskills.io/specification)
- File references: "use relative paths from the skill root" and "Keep file references one level deep from `SKILL.md`. Avoid deeply nested reference chains." — [specification](https://agentskills.io/specification)
- Validation: "`skills-ref validate ./my-skill`" checks frontmatter and naming conventions. — [specification](https://agentskills.io/specification)
- Anthropic's platform docs add: `name` "Cannot contain reserved words: `anthropic`, `claude`" and cannot contain XML tags; "Always write in third person. The description is injected into the system prompt"; "For reference files longer than 100 lines, include a table of contents at the top". — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Claude Code relaxes and extends the spec: "All fields are optional. Only `description` is recommended"; `name` "Defaults to the directory name"; "the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing". Extra fields include `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `paths`, `shell`. — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- Claude Code locations: personal `~/.claude/skills/<skill-name>/SKILL.md`, project `.claude/skills/<skill-name>/SKILL.md`, plugin `<plugin>/skills/<skill-name>/SKILL.md` "invoked as `/plugin-name:skill-name`". — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- Claude Code context behaviour: "the rendered `SKILL.md` content enters the conversation as a single message and stays there across later turns"; "Claude Code does not re-read the skill file on later turns, so write guidance that should apply throughout a task as standing instructions rather than one-time steps"; after auto-compaction it "re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens." — [Claude Code skills docs](https://code.claude.com/docs/en/skills)
- Claude Code supports dynamic context injection: "The `` !`<command>` `` syntax runs shell commands before the skill content is sent to Claude." "A failed command aborts the entire skill invocation". — [Claude Code skills docs](https://code.claude.com/docs/en/skills)

### Inferences
- For a long-running port, the 5,000-token re-attachment limit after compaction means the rules that must survive a long session (verification gates, "read the state file first") belong in the first part of `SKILL.md`, with language-mapping tables in `references/`.
- A portable skill should satisfy the stricter agentskills.io rules (name matches directory, 1,024-char description, space-separated `allowed-tools`) and treat Claude Code-only fields as optional extras that other agents ignore.
- Dynamic injection (`` !`cat state-file` ``) is a Claude Code-only way to load the port's progress file at invocation; it fails the whole invocation if the command fails, so the command needs a fallback.

### Gaps
- The last ~20,000 characters of the Claude Code skills page were not read (truncated at 100,000 characters), so later sections (for example troubleshooting or sharing) are not covered.
- GitHub Copilot's and Codex's own skill-format documentation (docs.github.com, developers.openai.com) were not fetched; compatibility of the extra fields there is unverified.

## 4. What do well-regarded skill authors recommend for long-running, multi-session work?

### Takeaway
The consistent advice is to keep state on disk rather than in the conversation (a progress or state file, a machine-readable work queue, git commits), work one unit at a time behind verification gates that a script decides, use copyable checklists, and stop at explicit human sign-off points.

### Cited Findings
- Anthropic Engineering, "Effective harnesses for long-running agents" (Justin Young, published 2025-11-26): the first session "uses a specialized prompt that asks the model to set up the initial environment"; "Every subsequent session asks the model to make incremental progress, then leave structured updates." The initializer creates "a claude-progress.txt file that keeps a log of what agents have done" and a JSON feature list that coding agents "edit ... only by changing the status of a passes field". Agents are "asked to work on only one feature at a time", should "commit its progress to git with descriptive commit messages", and at session start "Read the git logs and progress files to get up to speed on what was recently worked on." — [anthropic.com/engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic skill best practices: "For particularly complex workflows, provide a checklist that Claude can copy into its response and check off as it progresses." "Common pattern: Run validator → fix errors → repeat". The "plan-validate-execute" pattern has Claude "first create a plan in a structured format, then validate that plan with a script before executing it"; it applies to "Batch operations, destructive changes, complex validation rules, high-stakes operations." "Prefer scripts for deterministic operations". — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- agentskills.io best practices: "An explicit checklist helps the agent track progress and avoid skipping steps, especially when steps have dependencies or validation gates." Validation loops: "do the work, run a validator (a script, a reference checklist, or a self-check), fix any issues, and repeat until validation passes." — [best-practices.mdx](https://github.com/agentskills/agentskills/blob/main/docs/skill-creation/best-practices.mdx)
- Anthropic "Evaluation-driven development" for skills: "Create evaluations BEFORE writing extensive documentation"; "Build three scenarios that test these gaps"; "Establish baseline: Measure Claude's performance without the Skill." — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Anthropic migration kit standing rules: "Queues live on disk. A unit of work is done when its output file exists at the path the naming rules dictate — never when an orchestrator remembers it. If you find yourself tracking state in conversation, stop and write a manifest instead". "Sign-off gates end the workflow ... Do not proceed on inferred approval. The human re-invokes the next phase; resumability is free because of rule 2." "The rulebook is read-only inside any loop." "Reviewers are adversarial, separate, and read-only." "Recurring failures move upstream." "The old code is the spec ... Never skip, delete, or weaken a test to make a queue shrink". — [CLAUDE.md](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/CLAUDE.md) (repo 800 stars, sub-threshold)
- The kit README's doctrine: "you don't fix the code — you fix the process that produced the code"; "No judge, no exit condition." — [README](https://github.com/anthropics/code-migration-kit-with-claude-code/blob/main/README.md)
- `code-modernization`: "State lives in files, not in chat"; verification is "built from evidence a script can check, not from the model's opinion"; "A run that executed no tests, or skipped them, is a failure"; "A deliberate one-line break must turn tests red (the canary)"; "Every verdict is computed again from current evidence each time; none is carried over from an earlier run." "One pilot unit first with its lessons written down, then batches." — [README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md)
- obra/superpowers `writing-plans` saves plans to `docs/superpowers/plans/<filename>.md` with tasks whose "Steps use checkbox (`- [ ]`) syntax", each task following write failing test -> verify it fails -> implement -> verify it passes -> commit. `subagent-driven-development`: "Fresh subagent per task + task review (spec + quality) + broad final review = high quality, fast iteration". — [writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md), [subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- mattpocock `handoff` skill: "Compact the current conversation into a handoff document for another agent to pick up." — [handoff SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/handoff/SKILL.md)
- Sub-threshold porting skills converge on the same shape: suifei's skill keeps "all state ... in YAML files in the workspace, readable by any AI agent or human" with `migration-state.yaml` as "SESSION ENTRY POINT: read this first every session"; mizchi's lists release gates and says "Never hand-write expected fixtures. Generate them from a pinned source runtime". — [suifei SKILL.md](https://github.com/suifei/lang-migration-skill/blob/main/SKILL.md), [mizchi SKILL.md](https://github.com/mizchi/skills/blob/main/translate-programming-language/SKILL.md)

### Inferences
- A custom Python -> .NET porting skill should define a single state file read first in every session, a per-unit manifest (module -> status) that only flips after a scripted parity check passes, and human gates between phases. These three elements appear independently in Anthropic's harness article, both Anthropic migration artefacts, and the sub-threshold porting skills.
- The verification gate should be a bundled script rather than prose, matching both the "prefer scripts for deterministic operations" guidance and the `compare.py` / `proof_pack.py` pattern in `code-modernization`.
- A rulebook of translation decisions that agents may cite but not edit mid-loop is a migration-specific addition not present in the generic skill-authoring guidance.

### Gaps
- No source was found that evaluates these long-running patterns specifically for skills (as opposed to harnesses or plugins) with measured outcomes.
- The Anthropic migration article on claude.com was identified through search results but not fetched in full; details attributed to it here come from the kit README and the search summary only.
