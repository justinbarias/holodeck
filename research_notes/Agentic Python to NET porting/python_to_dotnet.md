## 1. Semantic pitfalls when translating Python to C#

### Takeaway
Most port bugs are silent semantic differences, not syntax: integer overflow/division/modulo, rounding and float-to-string, UTF-16 vs code points, culture-sensitive formatting, dictionary ordering, missing-vs-null in JSON, and the move from a single-threaded event loop to a thread-pool scheduler. Each has a mechanical C# answer (BigInteger/checked, explicit floor-div helpers, `Rune`, `InvariantCulture`, `OrderedDictionary<,>`, `required` + nullable annotations, `CancellationToken` + immutable/locked state), and several can be enforced by the compiler or analyzers, which is what makes them tractable for a coding agent.

### Cited Findings

Numbers
- Python `int` has unlimited precision; C# `int`/`long` are 32/64-bit and overflow wraps silently unless in a `checked` context. Use `long` + `checked` (or `<CheckForOverflowUnderflow>true`) by default and `System.Numerics.BigInteger` where Python code relies on big ints (hashes, token math, IDs). [D] — [Python numeric types](https://docs.python.org/3/library/stdtypes.html#numeric-types-int-float-complex); [C# checked/unchecked](https://learn.microsoft.com/dotnet/csharp/language-reference/statements/checked-and-unchecked); [BigInteger](https://learn.microsoft.com/dotnet/api/system.numerics.biginteger)
- Python `//` floors and `%` takes the sign of the divisor; C# `/` on integers truncates toward zero and `%` takes the sign of the dividend. `-7 // 2 == -4`, `-7 % 2 == 1` in Python; `-7 / 2 == -3`, `-7 % 2 == -1` in C#. Python `/` on ints returns float; C# `/` on ints stays integer. [D] — [Python binary arithmetic](https://docs.python.org/3/reference/expressions.html#binary-arithmetic-operations); [C# arithmetic operators](https://learn.microsoft.com/dotnet/csharp/language-reference/operators/arithmetic-operators)
- Both `round()` in Python 3 and `Math.Round` default to round-half-to-even, but `Math.Round` has overloads/`MidpointRounding` modes and `decimal` vs `double` behave differently; port explicitly. [D] — [Python round](https://docs.python.org/3/library/functions.html#round); [Math.Round](https://learn.microsoft.com/dotnet/api/system.math.round)
- Float formatting: .NET Core 3.0+ `double.ToString()` emits the shortest round-trippable string (like Python `repr`), but surface forms differ (Python `str(1.0)` is `1.0`, C# gives `1`; exponent spelling differs) and .NET formatting is culture-sensitive by default (decimal comma on some locales). Always pass `CultureInfo.InvariantCulture` for machine-readable output. [D] — [.NET Core 3.0 floating-point formatting](https://devblogs.microsoft.com/dotnet/floating-point-parsing-and-formatting-improvements-in-net-core-3-0/); [.NET globalization](https://learn.microsoft.com/dotnet/core/extensions/globalization)

Strings
- Python `str` is a sequence of Unicode code points; .NET `string` is UTF-16 code units. `len("😀") == 1` in Python, `"😀".Length == 2` in C#. Indexing, slicing, reversing, truncation (e.g. token/char limits, chunkers for vector stores) need `System.Text.Rune` / `EnumerateRunes()` or `StringInfo` for grapheme clusters. [D] — [Character encoding in .NET](https://learn.microsoft.com/dotnet/standard/base-types/character-encoding-introduction)
- String comparison in .NET has culture-sensitive overloads; ports should use `StringComparison.Ordinal`/`OrdinalIgnoreCase` to match Python's code-point comparison. [D] — [Best practices for comparing strings](https://learn.microsoft.com/dotnet/standard/base-types/best-practices-strings)

None, truthiness, typing
- Nullable reference types are compile-time annotations (warnings), not runtime enforcement; enable `<Nullable>enable</Nullable>` and treat warnings as errors so `Optional[T]` -> `T?` is checked by the compiler. [D] — [Nullable reference types](https://learn.microsoft.com/dotnet/csharp/nullable-references)
- Python truthiness (`if x:` false for `None`, `0`, `""`, empty containers) has no C# equivalent; C# requires a `bool`. Each `if x` / `x or default` must be translated to the specific check intended (`is null`, `.Count == 0`, `string.IsNullOrEmpty`). `x or y` is not `x ?? y` when `x` can be `0`/`""`/empty. [D] — [Python truth value testing](https://docs.python.org/3/library/stdtypes.html#truth-value-testing)
- Mutable default arguments are shared across calls in Python; C# optional-parameter defaults must be compile-time constants, so the pattern translates to `T? arg = null` + `arg ??= new()`. Code that depends on the shared-default bug/feature must be made explicit state. [D] — [Python FAQ](https://docs.python.org/3/faq/programming.html#why-are-default-values-shared-between-objects); [C# optional arguments](https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/named-and-optional-arguments)
- `Protocol`/ABC -> interfaces; C# has no structural typing, so every duck-typed call site needs a nominal interface or adapter. [D] — [C# interfaces](https://learn.microsoft.com/dotnet/csharp/fundamentals/types/interfaces)
- C# 15 (in .NET 11, GA 2026-11-10) adds `union` types with compiler-checked exhaustive `switch`, plus closed hierarchies. This is the first native target for Python `X | Y` unions and Pydantic tagged unions; on .NET 10 / C# 14 use sealed record hierarchies or the OneOf library. [S] — [C# 15 union types, 2026-04-02](https://devblogs.microsoft.com/dotnet/csharp-15-union-types/); [Explore C# 15, 2026-08-24](https://devblogs.microsoft.com/dotnet/explore-csharp-15); [.NET 11 overview](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/overview)

Collections
- Python `dict` preserves insertion order (language guarantee since 3.7). `Dictionary<TKey,TValue>` documents enumeration order as undefined. Where order is observable (YAML/JSON round-trips, prompt assembly, test snapshots) use `OrderedDictionary<TKey,TValue>` (added in .NET 9) or a list of pairs. [D] — [Python dict](https://docs.python.org/3/library/stdtypes.html#dict); [Dictionary remarks](https://learn.microsoft.com/dotnet/api/system.collections.generic.dictionary-2); [OrderedDictionary<TKey,TValue>](https://learn.microsoft.com/dotnet/api/system.collections.generic.ordereddictionary-2)
- `dict[key]` on a missing key raises `KeyError` in Python and throws `KeyNotFoundException` in C#, but `dict.get(k)` maps to `TryGetValue`/`GetValueOrDefault`, whose default for value types is `0`/`false`, not null. [D] — [Dictionary.TryGetValue](https://learn.microsoft.com/dotnet/api/system.collections.generic.dictionary-2.trygetvalue)

Generators, context managers, decorators
- Generators -> `IEnumerable<T>` with `yield return`; async generators -> `IAsyncEnumerable<T>` with `await foreach`, taking a `[EnumeratorCancellation] CancellationToken`. `generator.send()`/`throw()` have no equivalent and need a redesign (channels or an explicit state machine). [D] — [Async streams](https://learn.microsoft.com/dotnet/csharp/asynchronous-programming/generate-consume-asynchronous-stream)
- `with` / `async with` -> `using` / `await using` over `IDisposable` / `IAsyncDisposable`. `__exit__` can inspect and swallow the exception; `Dispose` cannot see it, so suppressing context managers (`contextlib.suppress`, transaction rollback-on-error) become `try/catch/finally` or exception filters. [D] — [Implement DisposeAsync](https://learn.microsoft.com/dotnet/standard/garbage-collection/implementing-disposeasync)
- Decorators have no single equivalent. Mapping by purpose: registration/metadata -> attributes (+ reflection or source generator); cross-cutting wrap -> ASP.NET Core middleware / endpoint filters / `DelegatingHandler` / `DelegatingChatClient`; retry/caching -> Polly / `Microsoft.Extensions.Http.Resilience`; CLI command decorators -> System.CommandLine or Spectre.Console.Cli command classes. [D] — [ASP.NET Core middleware](https://learn.microsoft.com/aspnet/core/fundamentals/middleware/); [HTTP resilience](https://learn.microsoft.com/dotnet/core/resilience/http-resilience); [Source generators](https://learn.microsoft.com/dotnet/csharp/roslyn-sdk/#source-generators)

Async
- asyncio runs coroutines on one thread; code between `await`s is atomic with respect to other coroutines. .NET continuations run on thread-pool threads, so the same code after translation can run in parallel. Any module-level dict/list mutated from async code needs `ConcurrentDictionary`, a lock/`SemaphoreSlim`, `Channel<T>`, or immutability. [D] — [asyncio development notes](https://docs.python.org/3/library/asyncio-dev.html); [Task-based async pattern](https://learn.microsoft.com/dotnet/standard/asynchronous-programming/task-based-asynchronous-pattern-tap)
- Calling a coroutine in Python does nothing until awaited; calling an `async` method in C# starts it immediately (hot task). `asyncio.gather` -> `Task.WhenAll`; `asyncio.create_task` fire-and-forget needs explicit exception observation. [D] — [TAP](https://learn.microsoft.com/dotnet/standard/asynchronous-programming/task-based-asynchronous-pattern-tap)
- ASP.NET Core has no `SynchronizationContext`, so `ConfigureAwait(false)` is unnecessary in app code; it still matters in general-purpose libraries. Blocking with `.Result`/`.Wait()` is the equivalent of blocking the event loop and risks thread-pool starvation. [D] — [ConfigureAwait FAQ](https://devblogs.microsoft.com/dotnet/configureawait-faq/)
- Cancellation is cooperative and explicit: thread a `CancellationToken` through every async API (analyzer CA2016 flags missed forwarding). asyncio injects `CancelledError` at the next await; .NET throws `OperationCanceledException` only where the token is checked. [D] — [Cancellation in managed threads](https://learn.microsoft.com/dotnet/standard/threading/cancellation-in-managed-threads); [asyncio task cancellation](https://docs.python.org/3/library/asyncio-task.html#task-cancellation); [CA2016](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca2016)
- Temporal-specific trap: inside .NET workflows, standard Task APIs that default to `TaskScheduler.Default` break determinism. Use `Workflow.DelayAsync`, `Workflow.UtcNow`, `Workflow.Random`; do not use `ConfigureAwait(false)`, `Task.Run`, timers, `DateTime.UtcNow`, `Guid.NewGuid` in workflow code. Temporal docs recommend disabling analyzer VSTHRD105 in workflow projects. No first-party Temporal analyzer was found; community analyzers exist (`sains1/temporal-dotnet-analyzers`, `TemporalCommunity.Extensions.Analyzers` 0.6.0). [S] — [Temporal .NET workflow basics](https://docs.temporal.io/develop/dotnet/workflows/basics); [Introducing Temporal .NET](https://temporal.io/blog/introducing-temporal-dotnet); [community analyzers](https://github.com/sains1/temporal-dotnet-analyzers); [NuGet](https://www.nuget.org/packages/TemporalCommunity.Extensions.Analyzers)

Pydantic -> records + System.Text.Json (STJ)
- STJ polymorphism (since .NET 7) uses `[JsonPolymorphic]` + `[JsonDerivedType(typeof(X), "discriminator")]`; discriminators may be string or int. By default the discriminator must be the first property in the object; set `AllowOutOfOrderMetadataProperties = true` (.NET 9+) to accept Pydantic/YAML-originated payloads where it is not first (cost: buffering on large streamed objects). [S] — [STJ polymorphism](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/polymorphism); [AllowOutOfOrderMetadataProperties](https://learn.microsoft.com/dotnet/api/system.text.json.jsonserializeroptions.allowoutofordermetadataproperties)
- .NET 10 validates clashes between the discriminator property name and real properties (e.g. a discriminator named `type` when the derived class also has `Type`), which is the common Pydantic `Literal["x"]` tag pattern; previously this failed with duplicate-property errors. [S] — [.NET 10 breaking change: property name validation](https://learn.microsoft.com/dotnet/core/compatibility/serialization/10/property-name-validation)
- Pydantic distinguishes "field missing" from "field is None" and rejects/ignores extras by config. STJ equivalents: `required` members, `JsonSerializerOptions.RespectNullableAnnotations` (.NET 9), `RespectRequiredConstructorParameters`, and `JsonUnmappedMemberHandling.Disallow` for `extra="forbid"`. Defaults are permissive, so set them once in a shared options instance. [D] — [STJ nullable annotations](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/nullable-annotations); [STJ missing members](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/missing-members)
- Pydantic coerces types (e.g. `"1"` -> `int`) in lax mode; STJ is strict unless `NumberHandling` is set. Decide per field and encode in tests. [D] — [JsonNumberHandling](https://learn.microsoft.com/dotnet/api/system.text.json.serialization.jsonnumberhandling)
- Validation: STJ does not validate. Options are DataAnnotations (`[Required]`, `[Range]`), `IValidatableObject`, the options pattern's `ValidateDataAnnotations().ValidateOnStart()`, or FluentValidation for cross-field rules (Pydantic `model_validator`). [D] — [Options validation](https://learn.microsoft.com/dotnet/core/extensions/options); [FluentValidation](https://docs.fluentvalidation.net/)
- .NET 10 adds built-in minimal-API validation: `builder.Services.AddValidation()`; `Microsoft.Extensions.Validation` uses a Roslyn source generator over endpoint parameter types (no runtime reflection), giving FastAPI-style automatic 400 responses. [S] — [ASP.NET Core validation overview](https://learn.microsoft.com/aspnet/core/validation/overview); [Tim Deschryver walkthrough](https://timdeschryver.dev/blog/aspnet-10-validating-incoming-models-in-minimal-apis)
- JSON Schema generation (Pydantic `model_json_schema()`): `System.Text.Json.Schema.JsonSchemaExporter` (.NET 9+) from `JsonSerializerOptions`/`JsonTypeInfo`, with `TransformSchemaNode` for descriptions; `AIJsonUtilities.CreateJsonSchema` in Microsoft.Extensions.AI for tool schemas. [S] — [Extract JSON schema](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/extract-schema); [AIJsonUtilities.CreateJsonSchema](https://learn.microsoft.com/en-us/dotnet/api/microsoft.extensions.ai.aijsonutilities.createjsonschema)

Errors, tests, module state
- Exceptions are idiomatic in both languages; C# has no checked exceptions and no standard `Result<T>`. C# 15 unions make result types practical on .NET 11; otherwise keep exceptions and map Python exception classes to a small C# hierarchy. [S for unions] — [C# 15 union types](https://devblogs.microsoft.com/dotnet/csharp-15-union-types/)
- Monkeypatching does not exist; replace with constructor injection + fakes/mocks, `TimeProvider` for clocks, `HttpMessageHandler` stubs for HTTP, and `WebApplicationFactory<T>` with service overrides for the server. Module-level singletons become DI registrations. [D] — [Dependency injection](https://learn.microsoft.com/dotnet/core/extensions/dependency-injection); [TimeProvider](https://learn.microsoft.com/dotnet/standard/datetime/timeprovider-overview); [Integration tests](https://learn.microsoft.com/aspnet/core/test/integration-tests)

### Inferences
- The highest-risk classes for an LLM-driven port are the ones that compile cleanly and pass happy-path tests: `%` and `/` on negatives, `x or default`, `len()`/slicing on non-BMP text, `Dictionary` order, culture-sensitive `ToString()`, permissive STJ defaults, and unsynchronised shared state. These are best caught by differential tests against the Python implementation, not by review.
- Put the numeric/string helpers (`FloorDiv`, `PyMod`, rune-aware slice) in one small library with property-based tests, and instruct the agent to use them rather than re-deriving semantics per call site.
- Choosing .NET 11/C# 15 buys native unions for Pydantic tagged unions and result types, at the cost of an STS runtime that is two weeks old and may not yet be supported by every dependency. Targeting .NET 10 LTS with sealed record hierarchies is the lower-risk default.

### Gaps
- [D]-tagged items were not re-fetched; they are long-stable documented behaviour, but exact wording should be checked if quoted.
- Not verified this session: how STJ serializes C# 15 `union` types out of the box.
- The `[ValidatableType]` attribute requirement for .NET 10 validation is reported inconsistently across third-party guides; check [the official page](https://learn.microsoft.com/aspnet/core/validation/overview).

## 2. Library equivalents for the representative stack

### Takeaway
Every element of the stack has a maintained .NET counterpart except the two agent runtimes: there is no official Claude Agent SDK or OpenAI Agents SDK for .NET. The .NET-native substitute is Microsoft.Extensions.AI (`IChatClient`) plus Microsoft Agent Framework 1.x, with the official Anthropic, OpenAI and MCP C# SDKs underneath.

## 3. Interop options for incremental (strangler-style) migration

### Takeaway
In-process embedding exists (CSnakes, Python.NET) but both bind the .NET process to a CPython runtime and its GIL; IronPython cannot run a modern Python 3.10+/Pydantic codebase. For an app that is already a CLI + HTTP server, a process boundary (HTTP/SSE, stdio, MCP) is the most practical seam, and the same boundary lets .NET tests call the Python implementation as a differential oracle.

### Cited Findings
- **CSnakes** (Anthony Shaw et al.): a .NET source generator + runtime that embeds CPython in-process via the C-API and generates typed C# methods from Python type hints; supports virtual environments, C-extensions, `uv`, NumPy `ndarray` <-> `Span`/`TensorSpan`, hot reload, and CPython 3.13 free-threading. README lists .NET 8-9 and Python 3.9-3.13 (another line says 3.8-3.13). [S] — [README](https://raw.githubusercontent.com/tonybaloney/CSnakes/main/README.md)
- CSnakes maturity: latest stable `CSnakes.Runtime` is 1.2.1 (2025-08-08); 2.0.0 has been in beta through 2026 (beta.350 on 2026-07-15), with no stable 2.0 found. [S] — [NuGet](https://www.nuget.org/packages/CSnakes.Runtime); [2.0.0-beta.341](https://feed.nuget.org/packages/CSnakes.Runtime/2.0.0-beta.341)
- **Python.NET (pythonnet)**: embeds CPython in .NET (and vice versa) with `dynamic`. Since 3.0 you must set `Runtime.PythonDLL` / `PYTHONNET_PYDLL` before `PythonEngine.Initialize()`; every call into Python must be inside `using (Py.GIL())`; multi-threaded use needs `PythonEngine.BeginAllowThreads()`. Objects are `dynamic`, so there is no compile-time typing. [S] — [README](https://raw.githubusercontent.com/pythonnet/pythonnet/master/README.rst)
- pythonnet maturity: a 3.1.0rc1 exists on PyPI with wheels tagged cp310-cp314; no final 3.1.0 or matching NuGet release was confirmed. [S, partial] — [PyPI 3.1.0rc1](https://pypi.org/project/pythonnet/3.1.0rc1/)
- **IronPython 3**: latest release found is 3.4.2 (Dec 2024, fixes .NET 9). It implements Python **3.4** syntax and stdlib plus selected later features (f-strings); targets .NET Framework 4.6.2, .NET Core 3.1, .NET 6. No CPython C-extensions. This rules out Pydantic v2 (Rust core), modern `asyncio` syntax usage, `match`, and most of the representative stack. [S] — [releases](https://github.com/IronLanguages/ironpython3/releases); [ironpython.net](https://ironpython.net/); [discussion: Bringing IronPython current](https://www.github.com/IronLanguages/ironpython3/discussions/1755)
- **Process boundary**: the MCP C# SDK provides client and server over stdio and HTTP, so either side can expose capabilities to the other as MCP tools during migration. [S] — [MCP C# SDK 1.0](https://devblogs.microsoft.com/dotnet/release-v10-of-the-official-mcp-csharp-sdk/)
- gRPC and HTTP are first-class in ASP.NET Core; YARP is Microsoft's reverse proxy for routing a subset of routes to a new service while the rest go to the legacy one (the documented incremental-migration pattern for ASP.NET). [D] — [gRPC on .NET](https://learn.microsoft.com/aspnet/core/grpc/); [YARP](https://learn.microsoft.com/aspnet/core/fundamentals/servers/yarp/yarp-overview); [Incremental ASP.NET migration](https://learn.microsoft.com/aspnet/core/migration/fx-to-core/inc/overview)
- Temporal supports polyglot workers: workflows and activities are addressed by name over task queues, so Python activities and .NET workflows (or the reverse) can coexist during migration. [D] — [Temporal task queues](https://docs.temporal.io/task-queue)
- Temporal's own cross-SDK `features` repo runs the same feature in Go, Java, TypeScript, Python and C# with a common runner and compares behaviour and history, i.e. a published example of the differential-oracle pattern. [S, via fork README] — [features (fork)](https://github.com/antlai-temporal/features)

### Inferences
- Recommended seam order for this app: (1) the CLI contract (argv in, stdout/exit code out) and the HTTP/SSE contract are already language-neutral; record Python outputs as golden files and replay against the .NET build (Verify snapshots). (2) Pure functions (YAML -> validated config -> JSON, JSON Schema output, prompt assembly) can be compared by a .NET test that shells out to `python -m ...` or `uv run` and diffs normalised JSON. (3) Backends can stay in Python behind HTTP or stdio until the .NET backend passes the same recorded scenarios.
- CSnakes is the better in-process choice for a typed codebase (it consumes type hints and generates typed signatures), but its stable line stops at .NET 9 / Python 3.13 per the README and 2.0 is still beta; treat it as a test-time oracle bridge, not a shipped dependency.
- In-process embedding of an asyncio application is awkward regardless of tool: the Python event loop and the .NET thread pool must be bridged, and the GIL serialises calls. A subprocess oracle avoids this entirely.
- LLM calls are non-deterministic, so differential tests must sit below the model boundary: compare request payloads sent to a stub provider, tool schemas, SSE event sequences from a scripted fake model, and validation errors.

### Gaps
- CSnakes documentation site was unreachable (`tonybaloney.github.io` not in the session's allowed network). Not confirmed: coroutine -> `Task` mapping, generator support, Native AOT support, .NET 10/11 and Python 3.14 support, what changed in 2.0, and documented limitations. Check [the docs](https://tonybaloney.github.io/CSnakes) and [repo](https://github.com/tonybaloney/CSnakes).
- pythonnet: final 3.1 release date, .NET 10 support, and free-threaded CPython support not confirmed.
- IronPython: no evidence of a release after 3.4.2; current status in late 2026 not confirmed.
- No published write-up was found of a team using the Python implementation as a live oracle from .NET tests for an agent framework specifically.

## 5. Experience reports and how dual Python/.NET projects keep parity

### Takeaway

## 6. .NET project conventions that give agents tight feedback

### Takeaway
Make the compiler the first reviewer: nullable + warnings-as-errors + analyzers in a single `Directory.Build.props`, pinned SDK and central package versions, `dotnet format --verify-no-changes`, a test runner on Microsoft.Testing.Platform, snapshot tests against Python-recorded outputs, and property-based tests for the semantic-gap helpers.

### Cited Findings
- `<Nullable>enable</Nullable>`, `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` (or `dotnet build -warnaserror`), `<AnalysisLevel>latest-recommended</AnalysisLevel>`/`AnalysisMode`, and `<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>` make type, nullability, quality and style violations fail the build. Put them in `Directory.Build.props` so every project inherits them. [D] — [Compiler options: errors and warnings](https://learn.microsoft.com/dotnet/csharp/language-reference/compiler-options/errors-warnings); [Code analysis overview](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/overview); [Customize your build](https://learn.microsoft.com/visualstudio/msbuild/customize-by-directory)
- Analyzer rules that directly target the Python-port pitfalls in section 1: CA1305 (specify `IFormatProvider`), CA1307/CA1310 (specify `StringComparison`), CA2016 (forward `CancellationToken`), CA2007 (`ConfigureAwait`, library code only), CA1849 (call async methods in async context). [D] — [Code quality rules](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/)
- `dotnet format --verify-no-changes` is the CI gate equivalent to Black/Ruff `--check`, driven by `.editorconfig`. [D] — [dotnet format](https://learn.microsoft.com/dotnet/core/tools/dotnet-format)
- Central Package Management (`Directory.Packages.props`, `ManagePackageVersionsCentrally`) keeps versions in one file, which reduces agent-introduced version drift; `global.json` pins the SDK and, on .NET 10, selects Microsoft.Testing.Platform as the `dotnet test` runner. [D]/[S] — [CPM](https://learn.microsoft.com/nuget/consume-packages/central-package-management); [test platforms overview](https://learn.microsoft.com/en-us/dotnet/core/testing/test-platforms-overview)
- Test runner: xUnit v3 (native MTP support, also VSTest), NUnit and MSTest support both platforms; TUnit is MTP-only and source-generated. One third-party benchmark (single author/machine) put full-suite `dotnet test` at MSTest 311 ms, TUnit 575 ms, xUnit v3 743 ms, NUnit 1.1 s. Under MTP the VSTest `--filter` syntax does not carry over for xUnit. [S] — [xUnit v3 MTP](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform); [Meziantou benchmark](https://www.meziantou.net/benchmarking-dotnet-test-frameworks-xunit-v3-nunit-mstest-and-tunit.htm); [migrating from VSTest](https://learn.microsoft.com/en-us/dotnet/core/testing/migrating-vstest-microsoft-testing-platform)
- Snapshot testing: Verify (VerifyTests) serializes results to `.verified.*` files and fails on diff; suitable for CLI output, JSON Schema, SSE transcripts. [D] — [Verify](https://github.com/VerifyTests/Verify)
- Property-based testing: FsCheck (usable from C#) and CsCheck (C#-first, with shrinking and model-based/metamorphic testing). [D] — [FsCheck](https://fscheck.github.io/FsCheck/); [CsCheck](https://github.com/AnthonyLloyd/CsCheck)
- STJ source generation (`JsonSerializerContext`) makes missing type registrations compile-time/startup errors and is required for trimming/AOT. [D] — [STJ source generation](https://learn.microsoft.com/dotnet/standard/serialization/system-text-json/source-generation)
- For Temporal workflow projects, follow the SDK's analyzer guidance (disable VSTHRD105; consider community determinism analyzers) and run workflow replay tests in CI. [S] — [Temporal .NET core application](https://docs.temporal.io/develop/dotnet/core-application); [analyzers](https://github.com/sains1/temporal-dotnet-analyzers)
- Give the agent current docs and curated practice: install relevant `dotnet/skills` plugins and connect the Microsoft Learn MCP server. [S] — [dotnet/skills](https://www.github.com/dotnet/skills); [Learn MCP](https://github.com/MicrosoftDocs/mcp)

### Inferences
- A workable fast loop mirroring the Python harness (Black/Ruff/MyPy/pytest): `dotnet build -warnaserror` (types + nullability + analyzers) -> `dotnet format --verify-no-changes` -> `dotnet test` with a filter for the touched area -> full suite plus differential/snapshot tests before commit. The first step replaces MyPy and most of Ruff in one command.
- Snapshot files generated from the Python implementation and checked into the .NET test project give the agent a per-scenario diff as its failure signal, which is more actionable than assertion messages.
- Property-based tests are the cheapest guard for the arithmetic/string helpers: generate inputs, run the C# helper and the Python oracle (or a recorded table), and compare.
- Banning escape hatches (`dynamic`, `object`-typed bags, `!` null-forgiving, `#pragma warning disable`) via analyzers/`BannedApiAnalyzers` carries over the source repo's "no `Any`/`getattr`" rule.

### Gaps
